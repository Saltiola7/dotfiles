# Scoped Try Omarchy project shares

The project-share launcher keeps the existing Exchange export and adds writable exports for `/Volumes/ext/git`, `/Volumes/ext/state/worktrees`, `/Volumes/ext/state/dbsctr/worktrees`, and `/Volumes/ext/state/discovery-worktrees`. The guest mounts them at the same absolute paths so existing Git worktree pointers can resolve. No parent `/Volumes/ext` or `/Volumes/ext/state` export is added. VM storage and its backups remain outside those exports.

The launcher checks known Try Omarchy and Lima storage roots for disk or EFI-variable files with multiple hard links and refuses to start if it finds one. This is a launch-time check, not a continuous kernel-enforced filter: a host-side hard link or relocation created after launch could expose a disk in an exported folder. Keep VM disks and aliases out of the four exports. Do not place live SQLite databases, container storage or other concurrently written host state on the shared folders.

The guest's root-owned `try-omarchy-project-shares.service` uses the installed Try Omarchy native 9p mount helper. It refuses nonempty or symlink mount paths and rolls back earlier new mounts if a later mount fails. If no project tags are offered, it skips them. The original `launch-identity-stable.command` remains available without the extra project exports; `launch-project-shares.command` uses the new runtime copy. Both retain the same VM disk and EFI variables and the stable application identity.

Basic read, write, rename, Git commit and Git worktree operations passed on disposable 9p test files. A second isolated clone verified that a Git worktree with `/Volumes/ext/git` absolute metadata resolves when the share is mounted at that same path. On the main VM, all four mounts were active after a clean launch. A project repository and an existing worktree resolved at their original absolute paths, and temporary host-to-guest and guest-to-host file writes succeeded. Git metadata pointing at host paths outside these four folders may not resolve; in particular, guest OpenCode/DBSCTR databases should remain guest-local. A host-held POSIX advisory lock did not prevent the guest from acquiring its own lock on the same file. A guest exclusive-create attempt did reject a file already created by the host, but this narrow test does not establish safe concurrent Git operations. Avoid concurrent host and guest writes to the same worktree; keep SQLite databases and container storage on a local filesystem.

The reviewable launcher diff and guest helpers are in this directory. The guest installer is staged in `~/Exchange`. The launcher checks the installed app's vendor-script checksum; after an app upgrade, review and refresh this external runtime before reuse.

To reconstruct the external runtime, verify the installed Try Omarchy vendor script and stable runtime against their recorded hashes first. Copy the reviewed stable runtime to a new `run-qemu-gpu-projects.sh`, then apply `project-shares.patch` from its parent directory with `patch -p1`. Review the diff and dry-run the launcher with a disposable VM before using it. Never replace the signed application bundle or an existing VM disk. The pinned launcher is specific to the currently reviewed app build and must be refreshed after vendor updates.
